Independent static review of the learning pipeline at commit `28b53abd`. Every finding below was re-checked against the code at that commit. Where a finding turned out to be already fixed or factually wrong at HEAD, that is stated with evidence instead of being copied forward. Paths are relative to `app/src/main/java/com/ai/assistance/operit/` unless stated otherwise.

## Stage A — signals and schema safety

### R01 — ObjectBox model does not contain the new entities (confirmed, but the entity12 premise is wrong)

Evidence: `app/objectbox-models/default.json` declares `lastEntityId: 11:3712699051976894545` and `modelVersion: 5`. The highest entity id present is 11 (`MemoryAutoSaveCandidate`). `TaskEpisodeEntity`, `SkillRevisionEntity` and `PendingReviewEntity` are declared as `@Entity` in `data/model/TaskEpisodeEntity.kt:12`, `data/model/SkillRevisionEntity.kt:13` and `data/model/PendingReviewEntity.kt:12`, each with a plain `@Id var id: Long = 0` and no explicit `@Entity(uid = ...)`, but none of them appears in `default.json`.

Correction to the original finding: there is no `entity12` and no `MemoryLedger` in this repository. A repo-wide search finds the strings only in prose — `AGENTS.md:49`, `core/chat/hooks/ArchitectRulesHook.kt:24`, `docs/TODO/reliable-learning-architect-20261016/01-design.md:23` and `docs/plans/rebrand-completion-2026-10-10.md:40`. No Kotlin symbol, no `@Entity`, no id 12 exists. The constraint in `AGENTS.md` therefore protects something that is not in the schema. It must still be honoured as written, but it does not constrain this work, and the risk of an id collision with entity 12 is not real at HEAD.

Why it matters: ObjectBox assigns entity ids and UIDs at annotation-processing time and records them in `default.json`. If the model file is not committed alongside the entity declarations, the next build regenerates ids from scratch. Two builds can then disagree about which id belongs to which entity, which produces unstable UIDs, a schema mismatch on open, and a database that fails to open after an app update on an installed device. Because the three entities are new and empty, the safe path is to commit the regenerated model together with the entity declarations in one change, before any of them holds user data.

Proposed fix: run the ObjectBox annotation processor once through GitHub-hosted Actions, commit the regenerated `app/objectbox-models/default.json` in the same commit as the entity declarations, and confirm that ids 12, 13 and 14 are assigned to the three new entities with stable UIDs. Do not hand-edit the JSON. Do not modify or renumber any existing entity. Verify update-over-existing-install by installing the previous build, then the new build, and confirming the database opens and existing memories are intact.

Acceptance test: `default.json` contains all three new entities with explicit ids and UIDs; a build from a clean checkout produces a byte-identical model file; an update-over-existing-install on a device opens the database and preserves existing memory rows.

#### R01 — implemented behaviour (A01, commit `9afd9627`)

`app/objectbox-models/default.json` now contains the three entities with stable ids and UIDs: `PendingReviewEntity` = `12:4325003580155501390`, `SkillRevisionEntity` = `13:990099011800972325`, `TaskEpisodeEntity` = `14:4269907125077724122`. The model was generated by the ObjectBox annotation processor through the new `ObjectBox Model` workflow (`.github/workflows/objectbox-model.yml`, run 39048652619, artifact `objectbox-model-1`) and is purely additive: existing entities 4-8 and 11 keep their ids, UIDs and properties; `lastEntityId` moved 11 → 14; `lastIndexId` moved 13 → 16 (three new indexes, one per entity); the retired UID lists and `modelVersion` (5) are unchanged. No UID was hand-written.

Status: model committed and CI-verified. Update-over-existing-install on a real device has NOT been performed and remains PENDING.

### R02 — Review signals are hardcoded false, so no review is ever enqueued (confirmed)

Evidence: `api/chat/EnhancedAIService.kt:2057-2070` constructs `ReviewTriggerPolicy.ReviewSignals` with `explicitUserCorrection = false`, `taskFailed = false`, `repeatedRepairCount = 0` and `complexSuccessWithReusableLesson = false`. The comment immediately above admits the intent: "Conservative signals keep this a no-op by default; plumbing exists for future wiring." `ReviewTriggerPolicy.decide` returns `shouldReview = false` for an all-false signal set, so `ReviewTriggerEnqueuer.maybeEnqueue` always returns false and the pending-review queue is never populated in production. The Reflector therefore never runs, and every downstream stage that depends on episodes is starved.

Why it matters: this is the single reason the whole learning loop is inert. Everything else in this document is downstream of a queue that never fills.

Proposed fix: derive the four signals from deterministic, observable outcomes rather than from model self-judgement. `explicitUserCorrection` from a detected correction turn; `taskFailed` from a terminal tool error or a failed build result; `repeatedRepairCount` from a counter of repair attempts within the turn; `complexSuccessWithReusableLesson` from a success that exceeded a step or tool-call threshold. Each signal must be computed from recorded events, not inferred by the model about itself.

Acceptance test: a turn containing an explicit user correction enqueues exactly one review; a turn with no correction, no failure and a short success enqueues none; a unit test asserts each signal maps to its event source.

#### R02 — implemented behaviour (A02, commit `cddaa1e0`)

The signals are now derived by `ReviewSignalDeriver` (`app/src/main/java/com/ai/assistance/operit/data/learning/ReviewSignalDeriver.kt`) from events recorded during the turn. `ReviewTriggerPolicy` remains the single decision point; the deriver only produces signals.

| Signal | Event source | Rule |
| --- | --- | --- |
| `explicitUserCorrection` | `TurnObservations.explicitCorrectionAction` only | Set ONLY by a deliberate user action recorded in `TurnObservations.explicitCorrectionAction`. Nothing in production sets it yet: there is no user-initiated "this reply is wrong" control in the app, and `regenerate` is a retry, not a correction marker. A lexical marker match does NOT set this signal. |
| `candidateCorrection` | The turn's conversation history (`MessageExecutionContext.conversationHistory`, `PromptTurnKind.USER` / `PromptTurnKind.ASSISTANT`) | True when an assistant turn precedes the last user turn in the same turn's history AND the trimmed, lower-cased user content matches one of `ReviewSignalDeriver.CORRECTION_MARKERS` on a word boundary. The markers are specific phrases; the bare `"wrong"` marker was removed because it matched "wrongly" and "nothing wrong with the build". A match is a weaker candidate signal, not an explicit correction. |
| `taskFailed` | `ToolResult.success` from `processToolResults`, and invalidated tool rounds from `processStreamCompletion` | True when at least one tool result in the turn reported `success = false`, or at least one truncated/unclosed tool round was invalidated (`truncatedToolRecoveryCount > 0`). |
| `repeatedRepairCount` | `ToolResult.success` from `processToolResults` | The number of failed tool results in the turn; each failed tool result is one repair attempt. |
| `complexSuccessfulTurn` | `ConversationRoundManager.getCurrentRound()` (model hops) and tool result count | True when the turn had no failed tool results and no invalidated tool round, AND it reached `COMPLEX_TURN_HOP_THRESHOLD` (3) model hops or `COMPLEX_TURN_TOOL_THRESHOLD` (3) tool results. It measures complexity and success only and never asserts that a lesson exists. |

Note (after R14): the raw observed events are retained alongside the interpreted booleans in `ReviewSignals.observed` (an `ObservedTurnEvents`), so a later reader can see what was observed and what was inferred. The table above describes behaviour after R14 (commit `72c98edc`, test fix `d3535a5a`).

Recording points: `MessageExecutionContext` carries a `TurnObservationAccumulator`; `processToolResults` records `toolResultCount` and `failedToolResultCount`; `processStreamCompletion` records `truncatedToolRecoveryCount` at both `truncatedToolRecovery != null` handling sites. `finalizeAssistantResponse` derives the signals and passes them to `ReviewTriggerEnqueuer.maybeEnqueue`, which calls `PendingReviewRepository.enqueue` exactly once when the policy returns `shouldReview`.

Tests: `app/src/test/java/com/ai/assistance/operit/data/learning/ReviewSignalDeriverTest.kt` — one test per signal mapping, a no-signal turn that enqueues nothing, and a correction turn that enqueues exactly one review.

### R03 — Scheduler drains the hardcoded `"default"` profile (confirmed)

Evidence: `api/chat/library/ReviewScheduler.kt:62-64` sets `val profileId = "default"` and builds `PendingReviewRepository(context, profileId)` from it. The enqueuer uses the real active memory space: `api/chat/EnhancedAIService.kt:2044-2046` resolves `profileId` from `memorySpaceIdOverride` or `preferencesManager.activeMemorySpaceIdFlow.first()`, and `api/chat/library/ReviewTriggerEnqueuer.kt:24` writes through `PendingReviewRepository(context, profileId)` with that value.

Why it matters: reviews are written into the active memory space's store and drained from the `"default"` store. Unless the user happens to be on `"default"`, the queue is never drained and reviews accumulate forever in a store nobody reads.

Proposed fix: resolve the profile id the same way the enqueuer does, and drain every memory space that has pending reviews rather than a single hardcoded one.

Acceptance test: with the active memory space set to a non-default id, an enqueued review is drained and produces an episode in that same space.

#### R03 — implemented behaviour (A03, commit `27a6cef1`)

`ReviewScheduler.drainPendingReviews` no longer hardcodes `profileId = "default"`. It enumerates memory spaces through `preferencesManager.memorySpaceListFlow` (the same API `MemoryAutoSaveScheduler` uses) and drains each space that has pending reviews. Each resulting episode is saved through `TaskEpisodeRepository(context, profileId)` using the same `profileId` the review was read from, so it lands in the space it was enqueued in. A failure in one space is logged with its space id and does not abort draining of the remaining spaces; `CancellationException` is rethrown so coroutine cancellation still propagates. Batch-delete, retry and locale behaviour are unchanged (Stage B).

Tests: `app/src/test/java/com/ai/assistance/operit/api/chat/library/ReviewSchedulerMemorySpaceTest.kt`.

## Stage B — scheduler robustness

### R04 — Batch deletion, unbounded retries, stuck PROCESSING rows, hardcoded language (confirmed)

Evidence: `api/chat/library/ReviewScheduler.kt:62-89`. The loop sets a single `processedAny` flag and, if any one review produced an episode, calls `pendingRepository.delete(ids)` with the whole batch id list — so reviews whose `reflect()` returned null are deleted without ever being processed. `MAX_REVIEWS_PER_RUN = 5` bounds batch size, not attempts; `PendingReviewRepository.markFailed` increments `attemptCount` but nothing ever reads it, so a permanently failing review is retried every `LOOP_TICK_MS = 60_000L` forever. `getPendingAndFailed` (`data/repository/PendingReviewRepository.kt:43-53`) queries only `STATUS_PENDING` or `STATUS_FAILED`, so a row left in `STATUS_PROCESSING` by a crash between `markProcessing` and `delete`/`markFailed` is never re-queried and leaks permanently. Line 76 passes `useEnglish = true` unconditionally, ignoring the user's locale, whereas `api/chat/enhance/ConversationService.kt:552` correctly computes `!LocaleUtils.usesChineseContent(context)`.

Why it matters: silent loss of reviews, an unbounded retry loop that burns model calls on a permanently broken item, a permanent leak of stuck rows, and English lessons generated for Chinese users.

Proposed fix: delete only the ids that succeeded; add an attempt cap with a terminal dead-letter status; add a startup sweep that returns stale `PROCESSING` rows to `PENDING`; derive `useEnglish` from the locale as `ConversationService` does.

Acceptance test: a batch of three where one fails deletes exactly two and leaves the third retryable; a review failing past the cap stops being retried; a row left in `PROCESSING` is recovered on the next start; a Chinese-locale user gets Chinese lessons.

#### R04 — implemented behaviour (B01 and B02, commits `79a17f54` and `68931d45`)

B01 (`79a17f54`): `ReviewScheduler.drainPendingReviewsForSpace` now decides each review individually through the new pure decision core `PendingReviewBatchPolicy` (`app/src/main/java/com/ai/assistance/operit/data/repository/PendingReviewBatchPolicy.kt`) and deletes only the ids that actually produced an episode. A review whose `reflect()` returned null is marked failed on its own and stays retryable; it is no longer deleted as collateral of a sibling's success. `PendingReviewEntity` gained a terminal `STATUS_DEAD_LETTER`, and a review that reaches `MAX_ATTEMPTS` (3) is dead-lettered: never retried, never deleted, and inspectable through `getDeadLettered()`. `ReviewScheduler.start()` runs a recovery sweep that returns `PROCESSING` rows older than `PROCESSING_STALE_AFTER_MS` (10 minutes) to `PENDING`, while leaving fresh `PROCESSING` rows alone. The per-space failure isolation from `58bedd67` is preserved: a failure in one memory space is logged with its space id and does not abort draining of the remaining spaces.

B02 (`68931d45`): `useEnglish` is no longer hardcoded. It is derived from the user's locale through the new pure decision core `ReviewLessonLanguage` (`app/src/main/java/com/ai/assistance/operit/data/learning/ReviewLessonLanguage.kt`), resolved once per batch, mirroring `LocaleUtils.usesChineseContent`. A Chinese locale (including region variants and upper-case codes) requests Chinese lessons; every other locale, and a blank code, requests English.

Limitation (B02): the generation language is NOT persisted with the lesson. `TaskEpisode` and `TaskEpisodeEntity` have no language column; adding one would change the ObjectBox schema and require regenerating `default.json`, which was out of scope. The language only shapes the Reflector request. Recording it is a follow-up requiring a model regeneration.

Tests: `app/src/test/java/com/ai/assistance/operit/api/chat/library/ReviewSchedulerBatchTest.kt` (9 tests: `batchOfThreeWithOneFailure_deletesExactlyTwo`, `reviewFailingPastMaxAttempts_isDeadLettered`, `deadLetteredReview_isNotRetried`, `reviewBelowMaxAttempts_staysRetryable`, `staleProcessingRow_isRecovered`, `freshProcessingRow_isLeftAlone`, `processingRowExactlyAtStalenessBoundary_isNotStale`, `nonProcessingStatus_isNeverStale`, `succeededReview_isDeleted`) and `app/src/test/java/com/ai/assistance/operit/data/learning/ReviewLessonLanguageTest.kt` (7 tests: `chineseLocale_requestsChinese`, `chineseRegionVariant_requestsChinese`, `englishLocale_requestsEnglish`, `otherSupportedLocale_requestsEnglish`, `uppercaseChineseCode_isStillChinese`, `blankCode_requestsEnglish`, `lessonLanguage_matchesUseEnglish`). `ReviewSchedulerMemorySpaceTest` (5 tests) is unchanged and still green.

Status: implemented and CI-verified at `d3535a5a` (the tree that contains B01 and B02 together, with green Android Build and Android Tests). Not device-verified.

## Stage C — retrieval and gap check

### R05 — `workspacePath` used as task context, single-token matching, `missingPrerequisites` never called (confirmed)

Evidence: `api/chat/enhance/ConversationService.kt:563-574` calls `TaskPreflightProvider.buildPreflightBlock(...)` with `currentTaskContext = workspacePath`, and `data/learning/TaskPreflightProvider.kt:16-30` forwards that string into `TaskPreflightFormatter.buildPreflightBlock`. A filesystem path is therefore tokenized and matched against prerequisite conditions. `data/learning/TaskEpisodeRetrieval.kt:75-80` implements `isPrerequisiteApplicable` as `conditionTokens.any { it in contextTokens }` — one shared token is enough — and `tokenize` (lines 99-104) has no stopword list, no stemming and no IDF. `missingPrerequisites` (`TaskEpisodeRetrieval.kt:65-68`) has exactly two call sites, both in `app/src/test/java/com/ai/assistance/operit/data/learning/TaskEpisodeRetrievalTest.kt` (lines 184 and 197); it is never called in production, so the applicability gate is never enforced in the shipped path.

Why it matters: the update-versus-fresh-install distinction that the existing test claims to prove passes only because the test sentences happen to avoid token overlap. In production a path containing a common token such as `storage` or `com` matches almost any prerequisite, so the gate is either always-on or never-on, and the missing-prerequisite check that would catch it is dead code.

Proposed fix: pass the actual task description as `currentTaskContext`; add a stopword list and require a match threshold rather than any single token; call `missingPrerequisites` in the production preflight path.

Acceptance test: a fresh-install task does not match an update-only prerequisite and vice versa, using sentences that deliberately share common tokens; a test asserts `missingPrerequisites` is reached from the production preflight path.

#### R05 — implemented behaviour (C01 and C02, commits `07cda3ea` and `55151c83`)

C01(a) (`07cda3ea`): `ConversationService.prepareConversationHistory` no longer passes `workspacePath` as `currentTaskContext`. It passes the actual user request text (the same `processedInput` used as `taskQuery`, capped at `PREFLIGHT_TASK_CONTEXT_MAX_CHARS = 800`) plus a bounded excerpt of the last `PREFLIGHT_RECENT_TURN_COUNT = 4` USER/ASSISTANT turns (capped at `PREFLIGHT_RECENT_TURNS_MAX_CHARS = 600`). `SYSTEM`, `TOOL_CALL`, `TOOL_RESULT` and `SUMMARY` turns are skipped. The `workspacePath` gate that decides whether preflight runs at all is unchanged.

C01(b) (`07cda3ea`): `TaskPreflightFormatter` now calls `TaskEpisodeRetrieval.missingPrerequisites` in the production preflight path, so the applicability gate is enforced in the shipped code rather than only in tests. "Satisfied" is deterministic and makes no model call: a prerequisite is evidently covered when its normalized key (lowercase, trimmed, whitespace collapsed) occurs as a substring of the normalized request text. Documented limit: a request that merely mentions a prerequisite is treated as covering it, so every remaining item stays framed as a caution to verify rather than as a mandate. `TaskPreflightProvider` no longer swallows failures with `runCatching {}.getOrDefault("")`; it catches explicitly, logs via `AppLogger.e`, and `""` is the documented "no block produced" no-op. Bounds: `MAX_EPISODES_IN_BLOCK = 5`, `MAX_CHARS_PER_FIELD = 240`, `MAX_PREREQUISITES_PER_EPISODE = 3`, `MAX_BLOCK_CHARS = 2000`.

C02 (`55151c83`): `isPrerequisiteApplicable` no longer matches on any single shared token. Both sides are reduced to meaningful tokens (tokenizer output minus `ENGLISH_STOPWORDS` and `CHINESE_STOPWORDS`, minus purely numeric tokens). A condition that reduces to no meaningful tokens is not applicable; a context that reduces to no meaningful tokens is not applicable. A condition is applicable only when at least `MIN_DISTINCT_MATCHED_TOKENS = 2` distinct meaningful tokens are shared AND the shared count is at least `MIN_MATCHED_FRACTION = 0.5` of the condition's meaningful tokens. There is no loosening fallback. `relevanceScore` and `rankRelevantEpisodes` also score on meaningful tokens.

| C02 threshold / list | Value |
| --- | --- |
| `MIN_DISTINCT_MATCHED_TOKENS` | 2 |
| `MIN_MATCHED_FRACTION` | 0.5 |
| `ENGLISH_STOPWORDS` | 111 entries |
| `CHINESE_STOPWORDS` | 101 entries |

Documented limits: the "satisfied" rule is a substring test on normalized text, so a request that merely mentions a prerequisite counts as covering it and the remaining items are always framed as cautions to verify; the CJK containment rule (see R06) requires a contiguous phrase, so a condition whose wording is paraphrased rather than repeated is not matched.

Tests: `app/src/test/java/com/ai/assistance/operit/data/learning/TaskPreflightFormatterTest.kt` (NEW, 6 tests: `buildPreflightBlock_applicablePrerequisiteNotEvident_rendersVerifyCaution`, `buildPreflightBlock_applicablePrerequisiteEvident_isNotRenderedAsCaution`, `buildPreflightBlock_nonApplicablePrerequisite_isNotRendered`, `buildPreflightBlock_manyEpisodesAndPrerequisites_staysBounded`, `buildPreflightBlock_neverUsesImperativeMandatePhrasing`, `buildPreflightBlock_chineseFraming_rendersChineseCautionLabel`) and 10 tests added to `TaskEpisodeRetrievalTest.kt` — 4 for C01 (`satisfiedPrerequisites_prerequisiteMentionedInRequest_isReturnedAsSatisfied`, `satisfiedPrerequisites_prerequisiteNotMentionedInRequest_isNotReturned`, `satisfiedPrerequisites_emptyRequest_returnsEmpty`, `satisfiedPrerequisites_blankPrerequisite_isNeverSatisfied`) and 6 for C02 (`isPrerequisiteApplicable_freshInstallation_doesNotMatchUpdateOnlyPrerequisite`, `isPrerequisiteApplicable_inPlaceUpdate_matchesUpdateOnlyPrerequisite`, `isPrerequisiteApplicable_pathLikeContext_doesNotMatchOnComOrStorage`, `isPrerequisiteApplicable_allStopwordCondition_isNotApplicable`, `isPrerequisiteApplicable_chineseUpdateVersusFreshInstall_behavesTheSame`, `rankRelevantEpisodes_stopwordsDoNotCreateRelevance`).

##### R05 — cancellation no longer swallowed (commit 4698f77e)

The defect: `TaskPreflightProvider.buildPreflightBlock` wrapped its suspend retrieval in `catch (e: Exception)`, which also caught `kotlinx.coroutines.CancellationException` and broke structured cancellation.

The fix: `CancellationException` is rethrown before the generic handler. The retrieval-and-format core was extracted to `buildPreflightBlockFrom(retrieve = ...)` so the rule is JVM-testable; the public function delegates with the real repository.

The same defect was found and fixed in `ReviewScheduler.runOnce()` (generic catch around the suspend drain) and in the `runCatching { ReflectorCurator.reflect(...) }` block in `drainPendingReviewsForSpace` (`runCatching` catches `Throwable`, including cancellation), which was replaced with an explicit try/catch that rethrows cancellation first.

Audited and confirmed NOT affected: `TaskEpisodeRepository` and `TaskEpisodeVectorIndex` contain only `try/finally` and no `catch`/`runCatching`, so cancellation already propagated; the `ConversationService` preflight call site has no local guard and relies on the provider, which now rethrows correctly. `ReviewScheduler.recoverStaleProcessing` and `drainPendingReviews` already rethrew cancellation and were left unchanged.

CI evidence: Android Build success https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39127121659 and Android Tests success https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39127121763 on commit `4698f77e`. Not device-verified.

### R06 — Latin-only tokenization, full-table scan, no vector or graph retrieval (confirmed)

Evidence: `data/learning/TaskEpisodeRetrieval.kt:99-104` tokenizes with `split(Regex("[^a-z0-9]+"))`, so Chinese, Japanese and Cyrillic text yields an empty token set and `rankRelevantEpisodes` returns an empty list for any non-Latin task. `data/repository/TaskEpisodeRepository.kt:26-35` implements `all()` as `episodeBox.query().build().find()` with no filter and no limit, and `retrieveRelevant` ranks that full list; the "bounded" claim applies only to the output `take(clampTopK(topK))`. Neither `TaskEpisodeRetrieval.kt` nor `TaskEpisodeRepository.kt` references a vector index, an embedding or `MemoryLink`, although `MemoryRepository` has both (`vectorIndexDir()` at `MemoryRepository.kt:363`, graph propagation at 1565-1608) and `docs/TODO/reliable-learning-architect-20261016/01-design.md` section 3 requires vector relevance plus graph links.

Why it matters: retrieval silently returns nothing for the app's primary Chinese-speaking users, and it degrades linearly with episode count because every query loads the whole table.

Proposed fix: tokenize with a Unicode-aware splitter that handles CJK; use the existing vector index for candidate generation and the `MemoryLink` graph for expansion, with a bounded candidate set instead of a full scan.

Acceptance test: a Chinese task retrieves relevant episodes; retrieval issues a bounded query rather than loading the full table; a test asserts the vector index and graph are consulted.

#### R06 — implemented behaviour (C03 parts a, b and c, commits `a364a032` and `b0bd7705`)

C03(a) (`a364a032`): the tokenizer is now Unicode-aware. It walks the text once, grouping characters into maximal CJK runs and maximal non-CJK word runs (`Character.isLetterOrDigit`). A non-CJK run is emitted as one token when its length is at least 2. A CJK run is emitted as every overlapping character bigram; a 1-character run is emitted as that character. CJK blocks covered: U+4E00-U+9FFF, U+3400-U+4DBF, U+3040-U+309F, U+30A0-U+30FF, U+AC00-U+D7AF. No `android.icu` and no `BreakIterator` are used. CJK applicability uses contiguous phrase containment: a condition containing CJK tokens is applicable when at least `MIN_CONTIGUOUS_CJK_BIGRAMS = 3` consecutive meaningful bigrams of the condition appear consecutively in the context (3 bigrams is a 4-character phrase; with 2, the 3-character phrase 新安装 would be shared by 全新安装 in a fresh-install context). Non-CJK conditions keep the C02 rule. The branch is chosen by whether the condition contains CJK tokens — one documented rule, not a fallback.

C03(b) (`a364a032`): `retrieveRelevant` no longer calls `all()`. It fetches at most `MAX_CANDIDATES_EXAMINED = 200` episodes with a bounded ObjectBox query ordered by `createdAt` descending, and ranks over that window. Documented trade-off: an older episode outside the recency window is not considered. `scoreEpisodes` returns scored candidates without the top-k clamp; `rankRelevantEpisodes` delegates to it.

C03(c) (`b0bd7705`): episodes can be embedded and searched with the existing vector infrastructure WITHOUT an ObjectBox schema change. `VectorIndexManager` and `IndexItem` are generic and file-backed, `CloudEmbeddingService` takes only a `Context`, and namespacing is a filename convention, so the episode index is a separate namespace under the same vector directory: `<filesDir>/.vector_index/episode_hnsw_<profile>_<dimension>.idx`, keyed by episode id. The embedding vector is NOT persisted on `TaskEpisodeEntity`; the index file is the only store. `TaskEpisodeVectorIndex` reuses `MemoryRepository`'s `sanitizeIndexKey` rule (trim, blank-to-`"default"`, replace `[^a-zA-Z0-9._-]` with `_`). When no embedding provider is configured, `isEnabled()` is false and `indexEpisode`/`searchEpisodeIds` are documented no-ops that log at debug level — the defined disabled state, not a fallback. Merge rule (`TaskEpisodeRetrieval.mergeCandidates`): union the lexical and vector candidate sets by episode id, add `VECTOR_CANDIDATE_BONUS = 0.5` to episodes also returned by vector search, sort by combined score then `createdAtMs` then `id`, and clamp once to `clampTopK`. The lexical path is a defined member of the union, not a fallback. `retrieveRelevant` and `TaskPreflightProvider.buildPreflightBlock` are now `suspend`. `TaskEpisodeRepository` gains `indexEpisode` (saves, then indexes `taskSummary` + `contextSummary` + `resolutionSummary`).

Tests: `TaskEpisodeRetrievalTest.kt` grew from 18 to 32 tests. C03(b) added 6 (`scoreEpisodes_returnsScoredCandidatesWithoutTopKClamp`, `mergeCandidates_vectorHitReceivesBonusAndOutranksLexicalOnly`, `mergeCandidates_tiesBrokenByCreatedAtMsThenId`, `mergeCandidates_emptyVectorIds_equalsLexicalRanking`, `mergeCandidates_resultIsClampedToTopK`, `maxCandidatesExamined_isAPositiveDocumentedCap`) and C03(c) added 2 (`mergeCandidates_vectorOnlyHitWithZeroLexicalScore_stillSurvivesViaBonus`, `mergeCandidates_lexicalEntryWinsOnDuplicateId`). C03(a) is covered by the previously `@Ignore`d `isPrerequisiteApplicable_chineseUpdateVersusFreshInstall_behavesTheSame`, which now runs and passes.

Status: parts (a), (b) and (c) implemented and CI-verified (both Android Build and Android Tests succeeded on `b0bd7705`: Android Build run https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39123568648 and Android Tests run https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39123568673; the `a364a032` runs were cancelled by the concurrency group and are covered by those green runs). ##### R06 — NOT implemented: graph expansion (C03 part d)

Graph expansion over `MemoryLink` is NOT implemented. `MemoryLink.source` and `MemoryLink.target` are `ToOne<Memory>` (`data/model/Memory.kt`) and `TaskEpisodeEntity` has no link field, so an episode cannot be linked to a memory or to another episode without a schema change. Implementing it requires a new ObjectBox entity (for example `EpisodeLinkEntity` with `sourceEpisodeId`, `targetEpisodeId`, `memoryId`) or new fields on `TaskEpisodeEntity`. Encoding ids into `MemoryLink.description` or `type` strings would give no referential integrity and no indexed traversal, so it is deliberately not faked. It is recorded as a follow-up comment in `TaskEpisodeRepository`. Intended edges: episode -> failure, episode -> fix, episode -> prerequisite.

By contrast, vector retrieval WAS implementable without a schema change: the vector index is a separate file namespace under the existing vector directory, keyed by episode id, and the embedding vector is not persisted on `TaskEpisodeEntity` — the index file is the only store. That is why C03(c) shipped and C03(d) did not.

##### R06 — indexing wiring fixed (commit 31314e1c)

The defect: `ReviewScheduler.drainPendingReviewsForSpace` called `episodeRepository.save(episode)`, the non-indexing save. `TaskEpisodeRepository.indexEpisode` — the only path that reached `TaskEpisodeVectorIndex.indexEpisode` — had zero callers in the repository, so the HNSW index file was never written and `searchEpisodeIds` always returned an empty list at its `if (!file.exists())` guard. The vector candidate generator was therefore permanently empty in production, which meant C03(c) was compiled and CI-verified but not effective.

The fix: the scheduler now saves through a documented helper that saves first and then indexes the saved episode id. `TaskEpisodeRepository` gained `indexSavedEpisode(episodeId, episode)` and a single pure text builder `episodeIndexText(episode)` (`taskSummary` + `" "` + `contextSummary` + `" "` + `resolutionSummary`), so there is exactly one text-building implementation. `indexEpisode` delegates to both.

THE EMBEDDING-FAILURE RULE, stated explicitly: indexing is secondary to saving the episode. The episode is saved first, so it is durable before any embedding request is made. If embedding or index writing then fails, the failure is logged at error level via `AppLogger.e` with the episode id and the review id, and the review is still treated as succeeded and deleted: an embedding failure alone must never mark the review failed or cause it to be retried, because the lesson itself was captured. This is an explicit, documented rule, not a silent catch. Cancellation is the one exception that is not handled there: it is rethrown so structured concurrency is preserved.

The disabled-provider case is the documented defined state of `TaskEpisodeVectorIndex.indexEpisode` (a no-op that returns), not a fallback: the episode is saved and nothing is logged as an error.

No `reindexMissing` method was added, and why: no production episode was ever indexed (`indexEpisode` had zero callers before this fix), so there is no historical backlog; the vector index is a derived cache populated by future saves.

Testability: an `EpisodeStore` interface was added as a JVM-testability seam (the scheduler needs an Android `Context` and ObjectBox, and the project has no Robolectric). `TaskEpisodeRepository` is the only production implementation; the scheduler's default factory preserves production behaviour exactly.

CI evidence: Android Build success https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39126148124 and Android Tests success https://github.com/Mavaebrook/HandleIT-Android/actions/runs/39126148173 on commit `31314e1c`. Not device-verified.

### R08 — CORRECTS/SUPERSEDES retires the target permanently with no check (confirmed)

Evidence: `api/chat/library/MemoryLibrary.kt:540-562`. When a link of type `CORRECTS` or `SUPERSEDES` is processed, the code calls `memoryRepository.markMemoryInactive(target)`. `markMemoryInactive` (`data/repository/MemoryRepository.kt:343-348`) writes `PROP_STATUS = STATUS_INACTIVE`, and nothing ever writes it back: the only other writer, `reinforceMemory` (lines 337-339), sets `STATUS_ACTIVE` only when the property is absent, so it can never reactivate an inactive memory. The link is matched by title only (lines 533-538, `findMemoryByTitle`), with no id and no content hash. There is no user confirmation, no consistency check that the two memories actually contradict, and no reactivation path. The inactive status is honoured at retrieval (`MemoryRepository.kt:1420`), so retirement is effective and therefore effectively irreversible.

Why it matters: the link type comes from an LLM extraction. A reversed link (the older fact marked as correcting the newer one) or a hallucinated link retires the correct fact permanently, and a title collision retires the wrong memory entirely. This directly violates the project requirement that a corrected fact must not be silently reverted.

Proposed fix: add a governance gate before retirement — verify the link direction against creation timestamps, check the target against active explicit user constraints, require confirmation for anything not clearly superseded, and make retirement reversible by recording the prior status and providing a reactivation path.

Acceptance test: a reversed link does not retire the newer fact; a retirement can be undone and the memory returns to active retrieval; a link whose target matches an active user constraint is refused.

### R09 — Promotion gate is too weak (confirmed)

Evidence: `data/learning/SkillRevisionLifecycle.kt:15` sets `const val MIN_INDEPENDENT_EVIDENCE = 1`. `evaluate` (lines 36-62) computes `passed = preserves && hasEvidence && noHarm`; `helpfulCount` is accepted and copied into the result but is not part of the predicate, so a candidate with zero helpful outcomes promotes on one evidence key. Evidence dedup is `normalize` (line 89) and `normalizeEvidenceKey` (`TaskEpisodeRetrieval.kt:106-108`), both of which only lowercase, trim and collapse whitespace — so two paraphrases of one incident count as two independent sources, contradicting the design note "Do not equate paraphrasing with new evidence". `preservesUserConstraints` (lines 22-29) compares only the candidate's self-declared `userConstraints` list against the authoritative list and never inspects `candidate.steps`, `checks` or `pitfalls`; it also returns `true` immediately when the authoritative list is empty.

Why it matters: a single incident can promote a skill revision, a paraphrase can fake independence, and a candidate can echo the constraint strings while its actual steps violate them.

Proposed fix: raise `MIN_INDEPENDENT_EVIDENCE` above one; require at least one helpful outcome; collapse paraphrases with a similarity threshold rather than string normalization; check the candidate's steps and checks against the constraints instead of trusting its self-report.

Acceptance test: a single-incident candidate is rejected; two paraphrases of one incident count as one source; a candidate whose steps violate a constraint is rejected even when its `userConstraints` list echoes the constraint.

### R10 — Reinforcement on text inequality, salience N+1, unconditional propagation floor (confirmed)

Evidence: `api/chat/library/MemoryLibrary.kt:435-439` and `464-467` call `reinforceMemory` whenever `newContent != memoryToContent` — a raw string comparison with no normalization, so a trailing space or a re-wrapped line counts as novelty. `MemoryRepository.kt:306-321` implements `loadMemorySalienceMetadata` with `memory.properties.reset()`, which discards the cached relation and forces a fresh query per memory; it is invoked per-memory from the search filter at `MemoryRepository.kt:1416-1420`, so the first pass over the candidate set issues one property query per memory. `MemoryRepository.kt:1575` defines `val basePropagationScore = 0.03 * effectiveEdgeWeight` and adds it to every traversed edge at lines 1590 and 1602 regardless of the source's relevance.

Why it matters: occurrence counts inflate on cosmetic edits, so they stop being evidence of usefulness; search cost grows with memory count; and a flat floor boosts semantically meaningless neighbours into results.

Proposed fix: reinforce only on semantic novelty (normalized comparison, or an embedding distance threshold); load salience metadata in one batched query; drop the unconditional floor and let edge weight alone determine propagation.

Acceptance test: a whitespace-only edit does not increment occurrences; a search over N memories issues a constant number of property queries; a zero-weight link contributes no score.

### R11 — Architect rules are global and prompt-only (confirmed)

### R12 — Episodes are injected into system prompts without provenance or sanitization (confirmed)

Evidence: episodes are produced by `ReflectorCurator.reflect` from raw user text (`api/chat/library/ReviewScheduler.kt:71-82`) and injected at `api/chat/enhance/ConversationService.kt:563-580` via `architectPreflightBlock`, consumed at `core/chat/hooks/ArchitectRulesHook.kt:66-74`. `TaskPreflightFormatter.buildPreflightBlock` interpolates `taskSummary`, `resolutionSummary`, `causeSummary` and `requiredPrerequisites` verbatim with no escaping and no delimiter fencing. The block header is a soft caveat only; there is no episode id, timestamp, source chat or confidence. Length is capped per field (`MAX_CHARS_PER_FIELD = 240`, `MAX_EPISODES_IN_BLOCK = 5`), so the block is bounded, but the cap is applied after the content is already trusted.

Why it matters: episode text originates as model output over past conversations and re-enters the system prompt with system-level authority. That is a prompt-injection path, and the model cannot tell which past task a lesson came from or how old it is.

Proposed fix: attach provenance (episode id, timestamp, source chat, confidence) to each injected lesson, sanitize and fence the content so it cannot be read as instructions, and keep a hard length cap on the whole block.

Acceptance test: an episode containing instruction-like text cannot alter behaviour when injected; every injected lesson carries an id and timestamp; the block stays under its cap.

### R13 — Newline-joined list fields are lossy (confirmed)

Evidence: `data/model/TaskEpisodeEntity.kt:61-65` and `data/model/SkillRevisionEntity.kt:68-72` both implement `joinList` as `joinToString("\n")` and `splitJoined` as `split("\n")`. Affected fields: `requiredPrerequisitesJoined`, `applicableConstraintsJoined`, `evidenceKeysJoined` on `TaskEpisodeEntity`; `prerequisitesJoined`, `stepsJoined`, `checksJoined`, `pitfallsJoined`, `evidenceKeysJoined`, `userConstraintsJoined` on `SkillRevisionEntity`. `PendingReviewEntity` has no list fields.

Acceptance test: a list element containing a newline round-trips unchanged through save and load.

### R16 — Keep trigger, confidence and promotion evidence separate (design rule)

This is a design rule for every later stage and for the schema, not a defect in a single file. Three concepts must stay distinct and must not be collapsed into one field or one decision:

- Review TRIGGER: a failure or a correction warrants investigation. A trigger establishes only that something is worth looking at; it does not establish why, and it does not establish that a lesson exists. R14 is the concrete case where a trigger was recorded as if it were a lesson.
- Lesson CONFIDENCE: a teacher or Reflector explanation is only a candidate. It is a hypothesis about cause, not a verified fact, and it must be stored as a candidate with its provenance.
- PROMOTION EVIDENCE: a successful held-out replay or a measured outcome. Only this can promote a lesson into the retrieval set.

Why it matters: collapsing these three is how a pipeline starts asserting lessons it never verified. R14's `complexSuccessWithReusableLesson` is a trigger recorded as a lesson; `causeIsHypothesis` (`data/model/TaskEpisodeModels.kt`) already exists to mark a cause as a hypothesis, and that distinction must be preserved rather than flattened.

Proposed fix: carry the three concepts as separate fields and separate decisions in the schema and in every stage. A trigger may open a review; a candidate explanation may be stored with confidence and provenance; only promotion evidence may move a lesson into retrieval. Reference this rule from Stages C, D and F.

Acceptance test: a review opened by a trigger alone produces no promoted lesson; a candidate explanation is stored with its provenance and is not retrievable as a lesson until promotion evidence exists; a promotion requires a recorded held-out replay or measured outcome.

### R14b — Neutral retry phrases still set the candidate correction signal (confirmed)

Evidence: `data/learning/ReviewSignalDeriver.kt:61-80` still lists `"redo"` (line 73) and `"try again"` (line 74) in `CORRECTION_MARKERS`. Commit `d3535a5a` ("test(learning): use marker-free text for the retry correction test") changed only the test input — `ReviewSignalDeriverTest.retry_doesNotSetExplicitCorrection` now uses `"Please run that again"` instead of `"try again"` — and left the marker list untouched (`git show --stat d3535a5a` shows exactly one file changed, the test). So a user who types a plain retry request such as "try again" or "redo" is still flagged as a candidate correction whenever an assistant turn precedes it. That is the retry-versus-correction conflation R14 set out to remove: the signal is candidate-only and bounded (it requires a preceding assistant turn and a word-boundary match), but it can still open a review for a turn that carries no correction.

Why it matters: a retry is a UI action (regenerate), not a statement that the previous answer was wrong. Treating the words "try again" or "redo" as a correction marker pollutes the review queue with turns where the user simply wanted another attempt, and it makes the candidate signal fire on ordinary instructions that happen to contain those words.

Proposed fix: remove or justify `"try again"` and `"redo"` and any similarly neutral request phrases from `CORRECTION_MARKERS`, keeping genuinely corrective phrases (for example "that's wrong", "that is wrong", "is wrong", "was wrong", "incorrect", "not what i asked", "you misunderstood"). Add tests that a plain retry request and an ordinary instruction containing those words do not set the candidate signal, while a clear push-back such as "that's wrong" still does.

Acceptance test: a turn whose last user text is a plain retry request ("try again", "redo") does not set `candidateCorrection`; an ordinary instruction containing those words does not set it; a clear push-back ("that's wrong") still sets it. This item is recorded only; the marker list and the test are not changed in this job.

- `ui/features/settings/screens/FunctionalConfigScreen.kt` lists `FunctionType.values()` automatically (line 165), BUT contains three exhaustive `when (functionType)` expressions with no `else` branch: the connection-test `when` (starts line 496), `getFunctionDisplayName` (lines 975-987) and `getFunctionDescription` (lines 993-1005). ### G02 — Dispatch-level action guard (partly present, gap confirmed)

Evidence: there is one central dispatch function, `AIToolHandler.executeTool` (`core/tools/AIToolHandler.kt:363`), through which tool invocations flow, and it already contains a pre-execution interception point, `checkToolInterception` (`AIToolHandler.kt:100`, called at line 365), which can return `AIToolHookDecision.Block`. That is a real hook. It is not, however, a complete hard gate:

- Enforcement is opt-in through registered `AIToolHook`s, and the only shipped hook, `ArchitectRulesSystemPromptHook` (`core/chat/hooks/ArchitectRulesHook.kt`), only injects prompt text. It has no interception and no blocking.
- Shell execution is reachable through multiple independent low-level paths that bypass the tool-dispatch layer entirely: `core/tools/system/shell/StandardShellExecutor.kt:108,225`, `core/tools/system/shell/RootShellExecutor.kt:307,386`, `core/tools/system/RootAuthorizer.kt:240,270,307,340`, `core/tools/system/Terminal.kt:101,141,157`, `util/PortProcessKiller.kt:32` and `core/tools/defaultTool/debugger/DebuggerUITools.kt:1319`.

So a guard placed only at `executeTool` would cover tool-dispatched calls but leave direct shell callers unguarded. This gap is recorded explicitly rather than claimed as a hard gate.

Why it matters: the project constraint that builds and tests never run on the VPS, local machine or PRoot is currently enforced only as text in the system prompt. A model that ignores the prompt can still reach a shell.

Proposed fix: enforce hard project constraints (never run Gradle or builds on VPS, local machine or PRoot; do not modify protected paths) at tool-dispatch time through the existing `checkToolInterception` hook, and additionally guard the direct shell-execution paths listed above, or record those paths as an accepted gap with a reason. Do not claim a hard gate until every path is covered.

Acceptance test: a tool-dispatched attempt to run a build is blocked at dispatch with a recorded reason; a direct shell-execution attempt through each listed path is either blocked or explicitly recorded as an uncovered gap; the guard is exercised by a test that asserts the block decision.

Stage placement: with Stage D, alongside D05.
