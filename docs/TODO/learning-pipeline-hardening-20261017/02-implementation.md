# Implementation sequence

Follow [the findings](01-findings.md) and update [the checklist](index.md) at every checkpoint. Each stage lists the old behaviour, the change, the expected result and a checkpoint. Do not start a stage before the previous stage's checkpoint is recorded.

## Stage A — signals and schema safety (A01-A03)
Old: the three new entities are declared in Kotlin but absent from the committed ObjectBox model, so ids and UIDs are regenerated per build; `ReviewSignals` is hardcoded to all-false so no review is ever enqueued; the scheduler drains the hardcoded `"default"` profile while the enqueuer writes to the active memory space.
Change: regenerate and commit `app/objectbox-models/default.json` together with the entity declarations, assigning stable ids and UIDs to `TaskEpisodeEntity`, `SkillRevisionEntity` and `PendingReviewEntity` without renumbering any existing entity; derive the four review signals from deterministic outcomes (explicit user correction, terminal tool failure, repeated repair count, complex success above a step threshold); resolve the scheduler's profile id the same way the enqueuer does and drain every memory space that has pending reviews.
Expected: the database opens after an update over an existing install with existing memories intact; a correction or failure turn enqueues exactly one review; a review enqueued in a non-default memory space is drained in that same space.
Checkpoint: the committed model file with the three new entity ids and UIDs, the signal-to-event mapping, a test per signal, and a CI run URL. Do not mark A01 verified before the update-over-existing-install check has actually run.

Amendment (2026-10-17, R14-R16): the signal derivation above is refined by R14. Store the raw observed event and its interpreted meaning as separate fields; rename or re-document the complexity signal so it only claims what it measures (it may trigger a review but must not assert a lesson exists); add an explicit user-initiated correction signal from a deliberate UI action and treat the lexical marker match as a weaker candidate signal. Schema lineage is refined by R15: A01 stays unchecked until an update-over-existing-install check runs on a device with an older build; before any future release, record which release first shipped entities 12-14 and keep default.json lineage from that release onward; clean-CI byte-identical regeneration is necessary but is not proof of upgrade compatibility. The design rule R16 applies from here on: keep review TRIGGER, lesson CONFIDENCE and PROMOTION EVIDENCE separate in the schema and in every later stage.

## Stage B — scheduler robustness (B01-B02)
Old: `drainPendingReviews` deletes the whole batch when any one review succeeds; failed reviews retry forever with no attempt cap; rows left in `PROCESSING` after a crash are never re-queried; `useEnglish` is hardcoded true.
Change: delete only the ids that succeeded; add an attempt cap with a terminal dead-letter status; add a startup sweep that returns stale `PROCESSING` rows to `PENDING`; derive `useEnglish` from the user's locale as `ConversationService` already does.
Expected: no review is lost or retried without bound; a crash mid-batch does not strand rows; Chinese-locale users receive Chinese lessons.
Checkpoint: a partial-failure batch test, an attempt-cap test, a crash-recovery test, a locale test, and the commit.

Implemented (2026-10-18): B01 and B02 are implemented and CI-verified at `d3535a5a` (B01 `79a17f54`, B02 `68931d45`). The per-review decision core is the new pure `PendingReviewBatchPolicy` (`MAX_ATTEMPTS = 3`, `PROCESSING_STALE_AFTER_MS = 10 min`, `dispositionFor`, `isStaleProcessing`): `drainPendingReviewsForSpace` decides each review individually, deletes only the ids that produced an episode, marks a review whose `reflect()` returned null failed on its own, dead-letters a review that reaches `MAX_ATTEMPTS` into the terminal `STATUS_DEAD_LETTER` (never retried, never deleted, inspectable via `getDeadLettered()`), and `ReviewScheduler.start()` sweeps `PROCESSING` rows older than the staleness bound back to `PENDING` while leaving fresh ones alone. The locale decision core is the new pure `ReviewLessonLanguage`, which derives `useEnglish` from the user's locale once per batch, mirroring `LocaleUtils.usesChineseContent`. Limitation: the generation language is not persisted with the lesson — `TaskEpisode`/`TaskEpisodeEntity` have no language column, and adding one would change the ObjectBox schema and require regenerating `default.json`, which was out of scope; recording it is a follow-up requiring a model regeneration. Tests: `ReviewSchedulerBatchTest` (9) and `ReviewLessonLanguageTest` (7); `ReviewSchedulerMemorySpaceTest` (5) unchanged and still green. R14 and R15 were implemented in the same job (`72c98edc` with test fix `d3535a5a`, and `2703b216`). Stage C is not started.

## Stage H01 — dedicated reviewer/teacher model (R17)

Placed after Stage B and before Stage D, because Stage D's Curator wiring depends on it.

Old: `ReflectorCurator.reflect` calls `EnhancedAIService.callFunctionModel` with `FunctionType.MEMORY` (`ReflectorCurator.kt:42`) and `ReflectorCurator.curate` calls it with `FunctionType.SUMMARY` (`ReflectorCurator.kt:69`), so reviews run on whatever model is mapped to those two function types. There is no review-specific model setting, and the model used for a review is not recorded anywhere.

Change: add a `REVIEW` function type to `data/model/FunctionType.kt`; route `ReflectorCurator.reflect` and `ReflectorCurator.curate` through it instead of `MEMORY` and `SUMMARY`; add its branches to the three exhaustive `when (functionType)` expressions in `ui/features/settings/screens/FunctionalConfigScreen.kt` (the connection-test `when` at line 496, `getFunctionDisplayName` at 975, `getFunctionDescription` at 993) and its string resources, including translations where the app ships them; give it a meaningful test-connection branch; and make the settings text state plainly that until the user picks a config the reviewer uses the DEFAULT config, and that review text (task summaries and context) is sent to whichever provider is selected. Reuse the existing model configs (`data/model/ModelConfigData.kt`: `apiEndpoint`, `apiKey`, key pool, `modelName`, `ApiProviderType` with 38 provider types); do not build a separate API url or key store. Record the model config id, model name and provider type used on every review (on the episode or the pending-review record, using a compatible metadata extension and a status or metadata string rather than renumbering anything) so the Stage F baseline-versus-same-model-versus-stronger-model comparison can be measured; leave that comparison explicitly UNMEASURED until replays exist. A reviewer may propose lessons but can never override explicit user constraints.

Expected: an existing install whose saved function mapping has no `REVIEW` key loads and gives `REVIEW` the default config (`FunctionalConfigManager.normalizeMapping` seeds every `FunctionType.values()` entry with `DEFAULT_CONFIG_ID` at index 0 and skips unknown saved keys); a review made after selecting a different config records that config's id and model; the Reflector and Curator no longer reference `MEMORY` or `SUMMARY`; the settings screen compiles with every `FunctionType` covered; the privacy text is present.

Checkpoint: the `REVIEW` enum value, the three `when` branches and string resources, the recorded model config id/name/provider on a review, the settings privacy text, the acceptance tests above, and the commit. The Stage F baseline/same-model/stronger-model comparison stays UNMEASURED until replays exist.


## Stage C — retrieval and gap check (C01-C06)
Old: `workspacePath` is passed as `currentTaskContext`; prerequisite matching accepts any single shared token with no stopword list; `missingPrerequisites` is never called in production; tokenization is Latin-only; retrieval is a full-table scan that ignores the vector index and the `MemoryLink` graph; the episode schema has no signature, omissions, structured conditions or warning feedback.
Change: pass the real task description as context; add a stopword list and a match threshold; call `missingPrerequisites` from the production preflight path; tokenize with a Unicode-aware splitter; use the vector index for candidate generation, and note that episodes are now actually written to that index by the review scheduler (commit `31314e1c`) — before that fix the scheduler used the non-indexing save, so the index file was never written and vector retrieval returned nothing in production; indexing is secondary to saving, so an embedding failure is logged with the episode id and never fails or retries the review (see the embedding-failure rule in 01-findings.md, R06); graph expansion over `MemoryLink` is deferred to C03d and is blocked on a schema decision, and is NOT part of the shipped Stage C work; cancellation is rethrown rather than swallowed in the preflight path and the review scheduler (commit `4698f77e`); add `taskSignature`, `omittedFromRequest`, `applicabilityConditions`, `trajectoryRef`, `warningsHelpful` and `warningsDismissed` as a compatible metadata extension; extend both Reflector prompts to emit `omitted_from_request` and `applicability_conditions` and extend `parseEpisode` to read them; add the plan-time gap check that retrieves 3-5 episodes, tests conditions, emits at most three caution-phrased warnings, records accept/dismiss and retires repeatedly dismissed lessons, attached to the existing planning call.
Expected: Chinese tasks retrieve relevant episodes; a fresh-install task does not match an update-only prerequisite even when the sentences share common tokens; a request that omits a prerequisite that mattered before produces at most three cautions and never a new user mandate; no unconditional extra model call per turn.
Checkpoint: the update-versus-fresh-install distinction demonstrated with deliberately overlapping sentences, a Chinese retrieval test, a bounded-query assertion, a warning-precision test, and the commit.

Amendment (2026-10-17): C06 is refined — dismissal is not evidence that a lesson is wrong. Record the dismissal reason and scope (not applicable here, already covered, wrong, noisy) and retire a lesson only on repeated reason=wrong or reason=noisy within comparable contexts; explicit user constraints never decay or retire through dismissal. Design rule R16 applies: a trigger opens a review, a candidate explanation is stored with confidence and provenance, and only promotion evidence moves a lesson into retrieval. G01 (per-lesson outcome tracking) is placed after this stage and before Stage F, because F depends on it.

## Stage D — skill lifecycle and governance (D01-D07)
Old: `ReflectorCurator.curate`, `SkillRevisionLifecycle` and `SkillRevisionRepository` have no production callers; a `CORRECTS`/`SUPERSEDES` link retires its target permanently on an LLM-extracted, title-matched link with no confirmation and no reactivation; `MIN_INDEPENDENT_EVIDENCE` is 1, helpful outcomes are not required, paraphrases count as independent evidence, and constraint preservation trusts the candidate's self-report; reinforcement fires on raw text inequality, salience metadata is loaded per memory, and a flat propagation floor is added to every edge; architect rules are injected into every workspace task in every project with prompt-only enforcement; episodes are injected into system prompts without provenance or sanitization; list fields are newline-joined and lossy.
Change: wire the Curator and the revision lifecycle into the post-review path, or record them as library-only with a visible note under T07-T10 in the existing index.md without deleting history; add a governance gate that verifies link direction and recency, checks active user constraints and makes retirement reversible; raise the evidence threshold, require a helpful outcome, collapse paraphrases by similarity and check candidate steps rather than self-reported constraints; reinforce only on semantic novelty, batch the salience query and drop the unconditional propagation floor; scope architect rules per project and either enforce the build restriction at dispatch or document the gap; add provenance, sanitization and a whole-block length cap to injected episodes; encode list fields losslessly.
Expected: a reversed or hallucinated link cannot retire the correct fact and any retirement can be undone; a single incident cannot promote a revision; a whitespace-only edit does not count as novelty; an unrelated project receives no HandleIT rules; an episode containing instruction-like text cannot alter behaviour.
Checkpoint: a reversed-link test, a reactivation test, a paraphrase-dedup test, a step-violation test, a query-count assertion, a cross-project scoping test, a prompt-injection test, a newline round-trip test, and the commit.

Amendment (2026-10-17): G02 (dispatch-level action guard) is placed with this stage, alongside D05. Enforce hard project constraints (never run Gradle or builds on VPS, local machine or PRoot; do not modify protected paths) at tool-dispatch time through the existing checkToolInterception hook in AIToolHandler.executeTool, and additionally guard the direct shell-execution paths (StandardShellExecutor, RootShellExecutor, RootAuthorizer, Terminal, PortProcessKiller, DebuggerUITools) or record those paths as an accepted gap. Do not claim a hard gate until every path is covered. Design rule R16 applies: a governance decision must not treat a trigger as promotion evidence.

## Stage E — trajectory log for future local-model migration (E01-E02)
Old: no raw trajectory record exists; episode summaries are lossy by design; retrieval uses only distilled summaries.
Change: add an append-only JSONL trajectory log separate from episode summaries, carrying a schema version, model id, system prompt version, playbook and skill versions, ids of retrieved episodes and skills, the prompt context, tool calls and results, the final response, an outcome label and correction pairs; redact secrets at write time, cap and rotate on device, exclude sensitive chats by default and record the embedding model name. Make raw trajectories the primary retrieval source and distilled skills a supplement, gated to hard or pattern-matching tasks. Superseded wording (amended 2026-10-17): "raw trajectories as the primary retrieval source" is superseded. Preserve full sanitized trajectories, retrieve compact episode indexes first, then expand only the relevant trace segments; raw traces are never fed in by default.
Expected: one well-formed record per completed turn with no secrets; the log rotates at its cap; an excluded chat produces no record; a hard task retrieves trajectories ahead of skills.
Checkpoint: a record-shape test, a secret-redaction test, a rotation test, an exclusion test, a retrieval-priority test, and the commit. Before any training use, check the provider terms for training on another provider's outputs and record the conclusion.

## Stage F — evaluation (F01-F02)
Old: no replay fixtures and no lesson A/B comparison exist; teacher-comparison evaluation was never measured.
Change: build replay fixtures from real tasks and compare baseline, with-lesson and without-lesson runs before promoting a lesson; tune retrieval weights and thresholds against the replays with automatic revert on regression. Superseded wording (amended 2026-10-17): the tuning clause is superseded. Tune only against held-out replay cases kept separate from the cases used to generate lessons, use versioned configurations with automatic revert on regression, and never optimize on the same set used to measure. Design rule R16 applies: promotion requires held-out replay or measured outcome evidence, not a trigger and not a candidate explanation.
Expected: a lesson is promoted only after a replay shows it does not regress the baseline; a regression automatically reverts the tuned weights.
Checkpoint: the fixture set, the measured comparison table, the revert mechanism, and the commit. Record only measured numbers; leave unmeasured comparisons marked pending.
